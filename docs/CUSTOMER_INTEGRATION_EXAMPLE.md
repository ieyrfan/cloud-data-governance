# Customer integration example

This is the short presentation story for an external application using DataSentinel. The external application is the customer. It does not screen-scrape the dashboard and it does not receive detected PII values.

```text
Customer system
    │ X-API-Key + Idempotency-Key
    ▼
DataSentinel Integration API v1
    │
    ├── create asynchronous document job
    ├── return short-lived upload contract
    ├── classify and redact through the existing engine
    ├── return sensitivity and signal types only
    └── issue audited protected-copy URL
```

## What the customer application does

1. Calls `GET /api/v1/whoami` to confirm its tenant and client identity.
2. Calls `POST /api/v1/documents` with an `Idempotency-Key`.
3. Uploads the file to the short-lived private S3 contract returned by the API.
4. Polls `GET /api/v1/jobs/{job_id}` until the status is `completed`.
5. Reads sensitivity, risk, document type and signal types. The response never contains detected values.
6. Calls `GET /api/v1/documents/{document_id}/protected-copy` to obtain a short-lived protected download URL.
7. Stores its own business result. DataSentinel returns a protected copy and audit correlation, not a permanent original route.

Run the working synthetic example from the project root:

```powershell
.\.venv\Scripts\python.exe scripts\customer_example.py `
  --base-url https://your-deployment.example `
  --client-file .datasentinel-integration-client
```

The ignored client file is generated by deployment. The example never prints the API key and uses synthetic NRIC/email values only.

Expected presentation output is similar to:

```text
Customer app identity: ifhx-demo / booth-client
Granted scopes: documents:create, documents:read, protected-copy:read
Job created: job_...
Upload complete: processing is asynchronous
Decision: RESTRICTED / CRITICAL
Document type: OTHER
Signals (types only): MALAYSIAN_NRIC, EMAIL
Protected copy available: True
Protected copy issued: expires in 120 seconds
Audit correlation: <uuid>
Customer result: the application receives a protected copy, never detected values.
Idempotency replay: True (same job returned)
```

## Why this proves the API is useful

- The customer application uses a machine contract, not the management console.
- A retry does not create duplicate work because the idempotency key returns the same job.
- Processing is asynchronous, so the customer application is not tied to Lambda execution time.
- The decision exposes useful types and risk without returning an NRIC or email value.
- The external API exposes a protected-copy route and no original-file route.
- Download-link issuance has an audit correlation ID.

## What this example does not claim

This example is a controlled synthetic acceptance flow. It proves the deployed Integration API contract, not production tenant onboarding, production quotas, WAF, malware quarantine, or zero-retention migration. The current Learner Lab stack still uses its existing temporary processing and protected-copy implementation; those boundaries are documented separately in `docs/CUSTOMER_CONTROLLED_ENCRYPTION_DESIGN.md`.
